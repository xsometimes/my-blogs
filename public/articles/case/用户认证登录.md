

## 用户认证登录相关
1. Access Token（访问令牌）和Refresh Token（刷新令牌）的关系
| **Token 类型**          | **生成时机** | **存储位置** | **使用场景**                                 | **类比情景**         |
|-------------------------|--------------|--------------|--------------------------------------------|----------------------------|
| Access Token            | 登录成功后   | 客户端       | 访问**受保护资源**（如 API 接口）               |临时门禁卡，有效期短，仅限进门| 
| Refresh Token           | 登录成功后   | **服务器**       | 用于获取新的 Access Token，延长会话有效期   |身份证，有效期长，用于补办门禁卡，不直接开门|


2. refreshtoken 相当于身份证，为什么还有过期时间
相当于身份证 + 自动签名的 “无限续杯券”，若永久有效，攻击者可无限次兑换资源，风险极高。

| 维度	| 身份证| 	RefreshToken| 
|-------------------------|--------------|--------------|
|权限范围|	证明身份，**需配合**其他凭证（如密码）	|**直接**用于获取新的 AccessToken（可访问资源）|
|泄露后果	|需结合其他信息（如户口本、密码）才能滥用	|攻击者可直接利用它刷新令牌，长期控制账户|
|存储环境	|物理保管（相对可控）	|存储在设备 / 服务器 / 网络中（面临数据泄露风险）|



现实中的折中设计：长有效期 + 灵活撤销：
- 默认有效期：常见设置：30 天、90 天，甚至 1 年（根据业务风险调整）。
- 主动撤销场景：
  - 用户主动登出（立即失效该设备的令牌）。
  - 检测到异常登录（如异地登录，强制失效所有旧令牌）。
- 令牌轮换机制
  - 每次使用 RefreshToken 时，生成新的 RefreshToken（旧令牌设置短时间过渡期后失效），类似 “滚动更新”，进一步降低风险

3. 多个 AccessToken 可以属于一个 User？
- 多设备 / 多客户端登录
- 权限分级与细粒度控制： 不同权限范围、临时令牌与长期令牌
  - 用户发起敏感操作（如转账）时，生成临时高权限令牌，操作完成后立即失效
- 安全性与令牌管理
  - 用户手机丢失后，在网页端撤销手机端的令牌，保留电脑端令牌的正常使用
  - 避免单点失效

在实际开发中，建议为每个 AccessToken 附加元数据（如 client_id、expires_at、scopes），并通过数据库或缓存管理令牌列表，确保既能灵活支持多场景，又能高效进行权限控制和安全审计。



4. Refresh Token 与 Access Token 的生成关系
1） 生成 AccessToken 时是否更新 RefreshToken？
- 标准轮换模式：是。优势：持续缩短 Refresh Token 的生命周期，降低泄露风险。
- 简化模式：否，仅更新 Access Token，保持 Refresh Token 不变。适用场景：对安全性要求较低的应用（如内部工具），或客户端存储能力有限的场景。

2）生成 RefreshToken 时是否重新生成 AccessToken？
- 常规流程：是，在用户首次登录（或 Refresh Token 初始化）时，同时生成 Access Token 和 Refresh Token。原因：用户登录后需立即获得访问资源的权限，不能依赖额外的刷新请求。


5. `@nestjs/passport `常见策略对比（场景化说明）

|策略	|使用场景	|典型流程|
|-------------------------|--------------|--------------|
|LocalStrategy|	用户名 + 密码登录（如网站登录页）|	1. 用户提交账号密码 → 2. 验证账号密码 → 3. 生成并返回 Token（如 JWT）。|
|JwtStrategy|	已登录用户的后续请求（如访问个人信息页）|	1. 请求头带 Token → 2. 验证 Token 有效性 → 3. 解析 Token 获取用户信息（如 ID、角色）。|
|OAuthStrategy|	第三方登录（如微信、GitHub 登录）|	1. 用户点击微信登录 → 2. 跳转到微信授权页 → 3. 获取授权码 → 4. 用授权码换用户信息 → 5. 生成 Token。|
|GoogleStrategy|	企业内部系统，强制用 Google 账号登录|	流程同 OAuth，但专门针对 Google 服务。|
|BasicStrategy|	简单的 HTTP 基础认证（如 Postman 测试接口时临时用）|	1. 请求头带 Authorization: Basic base64(用户名:密码) → 2. 解码并验证。|
|CustomStrategy|	自定义认证逻辑（如用短信验证码登录）|	1. 用户发验证码 → 2. 验证验证码 → 3. 生成 Token。|

6. 性能问题：每次请求都验证 Token？

JWT 验证是无状态的（直接验证签名），无需访问数据库，性能开销极小。

JWT 的结构：由三部分组成：Header（头部）、Payload（负载）、Signature（签名）

```ts
// 签名生成
Signature = HMACSHA256(
  base64UrlEncode(Header) + "." +
  base64UrlEncode(Payload),
  私钥
)
```
无状态：客户端请求时带上 JWT，服务器拿到后，解析 Header，重新计算签名（用同样的算法 + 同样的私钥），将重新计算的签名与客户端发来的 Signature 对比，无需经过数据库

7. 如何处理 Token 过期？
当 JWT 过期时，用 Refresh Token 获取新的 JWT，避免用户重新登录。

```ts
@Post('refresh')
@UseGuards(AuthGuard('refresh'))  // 自定义 Refresh Token 策略
refreshToken(@Request() req) {
  return this.authService.generateNewTokens(req.user);
}
```

8. 防止 Token 被冒用:
结合 Cookie 和 HttpOnly:将 Refresh Token 存储在 HttpOnly Cookie 中，防止 XSS 攻击。JWT 放在请求头中，定期轮换 Refresh Token。

|特性	|普通 Cookie	|HttpOnly Cookie|
|-------------------------|--------------|--------------|
|JS 可访问	|✅ 可以（document.cookie）	|❌ 禁止|
|XSS 风险	|高（攻击者可通过 JS 窃取 Cookie）	|低（JS 无法读取，攻击者拿不到）|
|用途	|存储前端需要的数据（如用户偏好）	|存储敏感数据（如 Session ID、Refresh Token）|

HttpOnly Cookie 如何解决这些问题？
- 防 XSS：即使网站存在 XSS 漏洞，攻击者也无法通过 JS 获取 HttpOnly Cookie。
- CSRF 仍需防范：HttpOnly 无法防御 CSRF，但可结合其他措施（如 SameSite 属性、CSRF Token）解决。

**完整流程**:
```plaintext
1. 用户登录 → 服务器生成：
   - JWT（Access Token） → 返回给客户端（存储在前端内存或 LocalStorage）
   - Refresh Token → 设置为 HttpOnly Cookie（客户端看不到，自动在后续请求中携带）

2. 客户端请求受保护资源 → 携带：
   - JWT 在请求头中
   - Refresh Token 在 Cookie 中（自动携带，JS 无法读取）

3. 当 JWT 过期 → 客户端用 Refresh Token 自动刷新，无需用户干预
```

**安全使用 Cookie**:
```ts
// 设置 Cookie 的示例（Node.js + Express）
import { Request, Response, NextFunction } from 'express';

// 设置 HttpOnly Cookie
app.post('/login', (req: Request, res: Response) => {
  // 验证用户登录...
  
  // 生成 Refresh Token
  const refreshToken = generateRefreshToken(userId);
  
  // 设置 HttpOnly Cookie
  res.cookie('refresh_token', refreshToken, {
    httpOnly: true,    // 禁止 JS 访问
    secure: true,      // 仅 HTTPS 生效
    sameSite: 'strict', // 防范 CSRF 攻击
    maxAge: 7 * 24 * 60 * 60 * 1000 // 7 天有效期
  });
  
  // 返回 Access Token（JWT）
  res.json({
    access_token: generateAccessToken(userId)
  });
});

// 读取 Cookie（服务器端）
app.get('/profile', (req: Request, res: Response) => {
  const refreshToken = req.cookies.refresh_token;
  // 验证 Refresh Token...
});
```

9. 为什么会有密码版本这个字段？

```tsx
const pv = await this.authService.getPasswordVersionByUid(request.user.uid)
// @ts-ignore
if (pv !== `${request.user.pv}`) {
  // 密码版本不一致，登录期间已更改过密码
  throw new BusinessException(ErrorEnum.INVALID_LOGIN)
}
```

request.user.pv 这个密码版本号(pv)是通过以下方式存储和传递的：

- 生成时机 ：
  - 当用户修改密码时，系统会生成一个新的密码版本号
  - 通常是一个递增的数字或时间戳
- 存储位置 ：
  - 存储在用户表中，作为用户记录的一个字段
  - 同时会编码到JWT token中，作为payload的一部分
- 传递过程 ：
  - 用户登录成功后，系统生成JWT token时会将当前密码版本号(pv)编码到token中
  - 每次请求携带JWT token时，token解码后会还原出这个pv值
  - 通过 request.user.pv 可以获取到token中携带的pv值
- 验证逻辑 ：
  - 代码中 this.authService.getPasswordVersionByUid 从数据库获取最新的pv
  - 与token中的 request.user.pv 比较
  - 如果不一致，说明用户修改过密码，当前token应失效

这种机制确保了：
- 用户修改密码后，所有之前的token自动失效
- 无需维护token黑名单，通过pv版本控制即可
- 增强了系统安全性，防止旧token被继续使用
